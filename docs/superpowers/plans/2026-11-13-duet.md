# Claude Duet Support Implementation Plan

**Goal:** Typed Duet client, a `claudesync duet` command suite, and a `duet/` export tree that `export-all` writes by default.

**Spec:** `docs/superpowers/specs/2026-11-13-duet-design.md` (binding; built from a captured session, NOT verified against the live API).

**Architecture:** A separate `DuetClient` in `packages/core/src/duet/` composes a `ClaudeSyncClient` through one new public method, `requestJson`. Sync logic (`runDuetSync`) depends on a narrow `DuetSource` interface (a `Pick` of `DuetClient`) so tests use plain fakes instead of stubbing `fetch`. A guarded wrapper, `runDuetSyncGuarded`, never throws, which is what `export-all` calls.

## Global constraints

- Node 24, pnpm, ESM, `.js` import extensions, strict TS, no `any`, ASCII only.
- Full TSDoc on every declaration and member, including internals (TSDoc style: no `{Type}`, use `@param name - desc`).
- Zod schemas use `.passthrough()`; only fields the code reads are required.
- Synthetic fixtures only. No network calls. Never print cookie values.
- Core tests: `pnpm --filter @infinite-room-labs/claudesync-core exec vitest run test/<path>`.
- Each task: failing test first, see it fail, implement, see it pass, commit. `git add` and `git commit` are separate calls.

## Task 1: `ClaudeSyncClient.requestJson`

- Files: `packages/core/src/client/client.ts`; test `packages/core/test/client/request-json.test.ts`.
- Tests: `returns parsed JSON through the paced request path`, `layers caller headers over auth headers case-insensitively`, `passes method and body through`, `maps 429 to RateLimitError`, `maps non-2xx to ClaudeSyncError with status`, `returns null for an empty body`.

## Task 2: Endpoints, schemas, types

- Files: `packages/core/src/duet/endpoints.ts`, `schemas.ts`, `types.ts`; tests `test/duet/endpoints.test.ts`, `test/duet/schemas.test.ts`.
- Tests: `builds every endpoint path with encoded segments`, `default headers carry the six observed headers`, `buildDuetHeaders fills the org header and applies overrides`, `project/channel/message/task/send/task-write schemas accept unknown extra fields`, `message requires id, body, created_at`, `task requires id and data.title`, `seq accepts string or number`.

## Task 3: `DuetClient`

- Files: `packages/core/src/duet/client.ts`; test `test/duet/client.test.ts`.
- Tests: `injects duet headers and keeps the session cookie`, `options.headers replaces and extends defaults`, `findProject posts find_only and parses`, `findProject returns null on 404 and 403`, `findProject rethrows other errors`, `listChannels url`, `getTimeline url and limit`, `getThread url`, `sendMessage body shape with generated client_message_id`, `sendMessage honors explicit client id and reply_to`, `sendMessage rejects blank text before any request`, `createTask generates a 33 char id`, `createTask honors explicit task id`, `updateTask sends title or done only`, `listTasks url`, `resolveChannelId default / id / name / unknown`.

## Task 4: Rendering and bucketing

- Files: `packages/core/src/duet/render.ts`; test `test/duet/render.test.ts`.
- Pure functions: `normalizeTimeZone`, `localDate`, `localTime`, `channelSlug`, `dayDirName`, `compareSeq`, `authorLabel`, `renderDayLog`, `renderDayReadme`, `isSuggestion`, `renderTasks`.
- Tests: `localDate buckets across a UTC-to-zone boundary`, `invalid or missing zone falls back to UTC`, `localTime formats HH:MM in zone`, `channelSlug appends the last 6 id chars and survives empty names`, `compareSeq orders numerically not lexically`, `authorLabel precedence`, `renderDayLog nests replies under roots with H2 and H3`, `renderDayLog writes bodies verbatim`, `renderDayLog treats a reply with no root as a root`, `renderTasks groups open, suggested, done newest first`, `renderTasks marks tasks absent from the last sync`.

## Task 5: `runDuetSync` and `runDuetSyncGuarded`

- Files: `packages/core/src/duet/sync.ts`; test `test/duet/sync.test.ts` (temp dirs via `fs.mkdtempSync`).
- Behavior: find project (null means `available: false`, nothing written); write `duet.json`; for each joined channel fetch the timeline, upsert into day stores, fetch threads for incomplete or orphaned roots, render and write only changed days through `writeTreeWithPreserve` with `INDEX.md` preserved; sync tasks for the project channel into `tasks.json` and `knowledge/TASKS.md`. Per-channel failure is reported and does not stop other channels. `runDuetSyncGuarded` converts any throw into `{ status: "failed" }`.
- Tests: `no-Duet account writes nothing`, `writes the documented tree`, `buckets by the thread root's local day across a zone boundary`, `late reply lands in its root's day`, `upsert keeps messages that left the fetched window`, `fetched message replaces the stored one by id`, `second run rewrites nothing`, `INDEX.md survives a day rewrite`, `fetches the thread when reply_count exceeds replies present`, `fetches the thread for an orphaned reply`, `tasks present flag flips to false when a task disappears`, `one failing channel does not stop the others`, `abort signal returns the partial tally`, `guarded sync reports a failure instead of throwing`, `guarded sync reports unavailable`, `duet.json holds no member lists`.

## Task 6: Public exports and CLI command suite

- Files: `packages/core/src/index.ts`; `packages/cli/src/commands/duet.ts`; `packages/cli/src/index.ts`.
- Commands exactly as in the spec: `status`, `channels`, `timeline`, `thread`, `send` (`-` reads stdin), `tasks [--all] [--suggested]`, `task add|done|rename`, `sync [--output]`. All take `--org`; read commands take `--json` and `--query`.
- No CLI test pattern exists in the repo, so CLI logic stays thin and the logic it relies on (channel resolution, guard, rendering) is tested in core. Verified by `pnpm build` and by running `--help` on the built binary (no network).

## Task 7: `export-all` integration

- Files: `packages/cli/src/commands/export-all.ts`.
- Duet sync runs after the org sync (skipped when interrupted) into the same output root via `runDuetSyncGuarded`; `--no-duet` skips it; every Duet outcome is one printed line and never touches the exit code. The guard itself is covered by the Task 5 tests.
